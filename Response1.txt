I. Authentication architecture
•	Authentication method: PIN-based demo login.
•	Endpoint: POST /api/auth/pin-login
•	Input: CustomerId and 4–6 digit PIN (validate length/format).
•	Verify PIN using a modern password-hashing algorithm with unique salt (Argon2 or BCrypt or ASP.NET Core PasswordHasher).
•	Store only salted one-way hash in CustomerCredentials.PinHash. Never log PIN or hash in answers/prompts.
•	On success:
•	Create a session record in CustomerSessions with a GUID SessionId and store a token hash (hash of session token). Issue the session token to client via secure HttpOnly, SameSite cookie OR return token in response (prefer cookie per spec).
•	Session expiry must be short-lived; support logout by marking RevokedOn.
•	On failure:
•	Increment FailedAttemptCount and, when threshold exceeded, set LockedUntil.
•	Provide safe error messages per spec.
•	Authorization:
•	On protected API calls and MCP tool invocations, server-side middleware must retrieve session and authenticated CustomerId from server-trusted session state.
•	Never accept CustomerId from the incoming chat content as an authorization source.
•	Authorization must enforce ownership predicates in the data access layer.
J. MCP architecture
•	NovaBanking.McpServer implements the fixed tool contract:
•	SearchBankingKnowledge(question) — public, routes to RAG / Azure Search.
•	GetCustomerProfile() — authenticated.
•	GetAccountSummary(), GetAccountBalance(accountId), GetRecentTransactions(accountId, count), GetLoanSummary(loanId), GetCreditCardSummary(cardId) — all authenticated.
•	Tool allowlist strictly enforced; Semantic Kernel must only be able to call that allowlist (tool invocation must be restricted in code/config).
•	MCP server accepts server-resolved customer context (not a model-supplied one). Kernel asks the API server to invoke MCP tools using the server's identity and must not pass a model-supplied CustomerId.
K. RAG architecture
•	Document sources stored in knowledge/ and mirrored to Blob Storage for ingestion.
•	Ingestion pipeline:
•	Text extraction from PDFs → cleaning → chunking (configurable chunk size/overlap) → metadata assignment (DocumentId, Title, Category, Version, EffectiveDate, PageNumber, SourceUrl) → embedding generation (OpenAI embedding model) → index into Azure Cognitive Search / vector store with metadata and embedding vector.
•	Query-time:
•	Azure Search returns top matching chunks with metadata.
•	Compose a grounded prompt including retrieved citations (title + metadata) and pass to Azure OpenAI via Semantic Kernel.
•	If no relevant content, return the explicit “I could not find this information…” message.
•	Must include prompt-injection defenses and treat retrieved content as untrusted.
L. Semantic Kernel orchestration architecture
•	Kernel acts as the orchestrator for incoming /api/ai/ask requests:
1.	Classify the question: public banking knowledge vs protected vs unsupported vs unsafe (pre-check rules and lightweight classifier).
2.	If public → call RAG pipeline (SearchBankingKnowledge).
3.	If protected → ensure the session is authenticated, inject authenticated CustomerId into the tool call context, and call appropriate MCP tool via allowlisted tool interface.
4.	Kernel must not be used to perform authentication or decide the CustomerId.
5.	Kernel must be configured with strict tool allowlist and must inject only minimal information into prompts (no PINs, no raw tokens, masked identifiers).
•	Kernel components:
•	Prompt templates, grounding templates, safety filters, and a tool-calling adapter that enforces server-side security.
M. The RAG + Semantic Kernel + MCP interaction (end-to-end)
•	/api/ai/ask receives user text.
•	Server validates request, optionally checks authentication state.
•	Server passes the text to Kernel orchestrator component which:
•	classifies intent,
•	routes to RAG or MCP,
•	constructs grounded prompt with retrieved chunks or uses MCP tool outputs,
•	calls Azure OpenAI to generate the final answer,
•	post-processes to mask any sensitive identifiers and adds citations,
•	logs audit metadata (not sensitive content) per audit contract.
